Обоснование проектов (1, 3, 5, 7):

1: цель — приложение доставки; результат — работающее приложение; срок — 4 мес.; участники — заказчик, РП, аналитик, разработчик, тестировщик.

3: цель — автоматизировать учёт студентов; результат — БД с интерфейсом; срок — ограничен; участники — заказчик, аналитик, разработчик БД, тестировщик.

5: цель — единое актуальное расписание; результат — веб-приложение; срок — ~3 мес.; участники — заказчик, РП, аналитик, разработчик, тестировщик.

7: цель — сайт на новом сервере; результат — работающий сайт с сохранённым контентом; срок — несколько дней; участники — сисадмин, разработчик, тестировщик.

Практическая работа №2 — паспорт проекта 
1. Название: Электронное расписание колледжа.

2. Проблема: изменения расписания теряются в чатах и на стендах, нет единого актуального источника.

3. Целевая аудитория: студенты, преподаватели, администрация.

4. Цель: за 3 месяца разработать веб-приложение с актуальным расписанием и возможностью его редактирования администрацией.

5. Результат: веб-приложение; БД расписания; просмотр по группе и преподавателю; поиск; отображение изменений; роли пользователей.

6. Участники:

Роль	                  Ответственность
Руководитель проекта	  Сроки, ресурсы, коммуникация
Аналитик	              Требования, сценарии
Разработчик	            Серверная и клиентская часть, БД
Тестировщик	            Проверка функционала и удобства
Заказчик	               Потребности, приёмка
7. Сроки: 3 месяца (анализ — 2 нед., проектирование — 2 нед., разработка — 6 нед., тестирование — 1 нед., внедрение — 1 нед.).

8. Ограничения: срок 3 мес.; команда 4 чел.; бюджет ограничен; платформа — веб; результат — работающий продукт.

9. Риски:

Изменение требований заказчиком → фиксировать требования, согласовывать изменения.

Болезнь участника → взаимозаменяемость, документация, резерв времени.

Проблемы с хостингом/интеграцией → заранее протестировать платформу, резервный вариант.
